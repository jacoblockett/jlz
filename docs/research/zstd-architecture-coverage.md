# Zstd-only architecture coverage, novelty collisions and research queue

**Started 2026-10-20. Status: ACTIVE, NOT EXHAUSTED.** Focus: the original native-Go JLZ on `main`, complete original 12-file Silesia, no Zstd executable/codec/backend in JLZ. This ledger is a **living, source-linked experiment register** for all major Meta Zstd ideas and their distinct JLZ placements. It is not a marketing claim that every possible algorithm or combination is enumerable or has already been tested. The researcher must mark the precise limits of a negative screen and retain plausible *structurally different* variants rather than rejecting an entire mechanism from one bad implementation.

**Current accepted reference:** 211,938,580 original B → **58,767,739 JLZ B / 4.7873709325 s encode / 1.8721679705 s decode**, retained ten complete original-Silesia medians, root PGO; reference Zstd-3 **66,216,569 B / 1.2561 / 0.8551 s**, historical XZ-6 **49,233,340 B / 116.9892 / 2.3079 s** (external CLI versus JLZ in-memory). No current integrated `candidate`.

## Evidence vocabulary

- **CURRENT**: JLZ already implements substantially this functionality; no novelty claim. Further different implementation can still be researched.
- **HISTORIC TEST**: concrete prior source/placement was actually coded and measured; only that concrete configuration can be closed.
- **NEW SCREEN**: this program actually encoded/decoded original-Silesia component samples, but no whole JLZ 10-run.
- **SOURCE AUDIT / OPEN**: upstream implementation was reviewed and JLZ counterpart/gap identified; **not** proof a JLZ candidate was tried.
- **NOT AUDITED**: even primary Zstd source mechanism is not sufficiently examined yet. Investigate before experimentation.
- **QUALIFIED CANDIDATE**: integrated native codec complete original 12-source archive with ten fully completed candidate-only encode/decode passes. Never infer this from source screens.
- **ACCEPTED / REJECTED**: concrete candidate decisions; avoid declaring the broader mathematical family impossible.

## Research discipline: no premature exhaustion

For each OPEN line, record **the specific pre-existing implementation and failed near-neighbor**, then inspect relevant actual upstream code and calculate the algorithmic novelty and likely max gain. Candidate exploration order:

1. **Theory and scope:** exact probability/entropy/copy/lookup mechanism, bytes and CPU it could save, memory dependence and decoder state; explain why previous negatives need not apply.
2. **Independent component trials:** exact native-Go inverse on original source **and** the matched actual selected stage, benchmarking against current complete native component framing rather than raw ideals.
3. **Supplementary placements:** try adding to the winning JLZ path, and plausible nonduplicative combinations; explicitly test replacement when justified. Preserve failed experiments and distinguish **untried variants**, not a fabricated "all possible".
4. **Refinement:** if gains exist, investigate alternative model/candidate coverage and no-double-encoding work elimination. Do not sweep arbitrary magic constants simply to claim completeness. Record the upper bound, measured total end-to-end CPU, decode incompatibility and decisive failure modes.
5. **Integrated candidate only if economically credible:** full original 12-file Silesia exact archives, **ten complete candidate-only encode+decode passes**, unaltered historical JLZ/Zstd/XZ anchors, input SHA manifest, old archives, vet/tests/race/Windows cross-build, per-file regressions, all framing/metadata charged.
6. **Decision:** accept on measured holistic improvement, reject a **specific** tested implementation when realistic gains cannot repay work, otherwise mark OPEN/DEFER with missing evidence. User's instruction to explore comprehensively is not a license to claim mathematically unlimited configurations have been exhaustively enumerated.
