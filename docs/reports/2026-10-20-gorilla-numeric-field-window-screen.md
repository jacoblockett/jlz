# Gorilla-style IEEE-754 significant-bit windows in already selected 28-byte record lanes

**Date:** 2026-10-20. **Disposition:** SCREENED and REJECTED this concrete supplementary numeric-field coding. No integrated JLZ candidate, no ten-run result, no decoder mode, no production or PGO changes.

## Exact prior-work and source audit

The source and placement audit was completed **before prototype code**. JLZ already selects a native **28-byte record-lane Huffman representation** for the full original Silesia `sao` file (7,251,944 original bytes; accepted archive 4,941,704 B). Prior tests rejected bytewise lag-28 XOR and modular subtraction before those same lanes: **5,285,575 B** and **5,268,655 B**, versus **4,941,467 B** current lane components, on all 28 independent original blocks. Another past screen rejected bytewise lag-8 XOR feeding lane coding. See [native LZP, field delta and bit-context screens](2026-10-20-native-lzp-field-delta-bitcontext-screens.md) and [fast adaptive/profile numeric screen](2026-10-20-full-corpus-profile-fast-adaptive-rejected.md). Generalized bytewise delta, 28-byte period re-detection and lane width variations are **CLOSED**.

The distinct mechanism here is **significant-bit window coding of whole 64-bit fields**, with explicit zero-run control bits and reuse of the preceding nonzero XOR's leading/trailing-zero window. This is **not** applying a bytewise XOR/delta to the entire record and then Huffman-coding all bytes. Audited the actual upstream [Prometheus Gorilla-derived XOR chunk source](https://github.com/prometheus/prometheus/blob/main/tsdb/chunkenc/xor.go) and [original Gorilla explanation and sources](https://github.com/keisku/gorilla). No external codec was used in JLZ, and the reversible trial was independently written in native Go.

## Experiment, corpus, and exact inverse

Used the unmodified Silesia ZIP original `sao` member from the 12-file corpus; original full-corpus manifest **12/12 SHA-256 MATCH** (all members already locally available, 211,938,580 B). Preserved root `default.pgo` SHA-256 `3b35cda74832360a252b63c1805e025aa1f4ed7a4fe4124d9a55929a6e86289f`. Current Go source was verified from `jlz-6a388ba91682.zip` against actual production paths on `main` (later commits since ZIP contain documentation, not altered production code).

Evaluated **all 28 independent original 256KiB natural source blocks** (last partial), and three distinct 8-byte-wide positions within the established modulo-28 record: byte offsets **0..7**, **8..15**, and **20..27**. The candidate encodes each complete 64-bit word's XOR against the preceding same-column word, a single bit if unchanged, otherwise significant bits framed by either a reused previous leading/trailing-zero window or an explicit 5-bit leading-zero / 6-bit significant-bit count. A 64-bit seed begins each block. Window reuse saves repeated framing. The decoder reverses every control bit into the **exact original 64-bit word** independent of whether the data are numerically valid IEEE values. Big-endian vs little-endian bits are handled deterministically by reading the native byte sequence as a little-endian `uint64`; encoding never rounds or converts floating values.

For comparable column cost, the reference **re-encoded the same complete-record bytes** in their eight separate existing JLZ `packStream` byte lanes (all real Huffman/RLE/raw frames included). The experimental column cost counts its real packed bitstream, **one byte selector**, one length varint for the word count and one for the bitstream. This is an **optimistically framed component screen**, not a new fully specified JLZ mode: partial bytes in source-block boundaries, surrounding 20 lane streams, block headers and model-choice flags are not fully accounted for. Component figures must not be called archive sizes or rigorous complete-frame winners.

Each field comprises **258,994 full 64-bit source values** across all 28 blocks, **all exactly decoded**; in total **776,982 values / 6,215,856 source bytes exact** under the candidate's Go encoder/inverse. Synthetic single, repeated, alternating and changing source patterns also passed, including an expected truncated-data failure. Component test runtime was about **0.33s wall** for all three field positions, **NOT a benchmark comparison** to complete JLZ. Source-aligned first field best winning block saved 4,608 B; its worst losing block expanded 10,291 B. The best per-block oracle at most **23,239 B** for this fixed bit-window placement before actual additional frame/selector and candidate comparison CPU. Across the original 211,938,580 B, that oracle is just **0.010965% of source**, even with perfect selection.

**Novelty matters:** the previous lag-28 signed/XOR transformations did not implement or charge adaptive leading/trailing-zero-window reuse, and their Huffman-coded byte residuals are not this stream. Conversely, the accepted JLZ lane model already exploits the nearly constant exponent bytes and frequent id/status fields, limiting what bit-window reuse adds. This establishes a new concrete negative at a complementary location, not a reason to tweak a previous failed lag delta threshold.

## Decision and subsequent focus

**REJECT exact Gorilla numeric-field replacement/supplement before expensive JLZ integration**. Only one field has any wins; saving opportunities are too small relative to needed runtime candidate selection, per-block bitwise encode/decode, decoder subtype and handling of edge bytes. There is no evidence of a new practical full-codec improvement; the tested proposal **cannot be counted as a ten-run candidate**. Do not vary Gorilla window bit counts, numerical field alignment or 28-byte stride to fabricate novelty. This does **not** close general floating-point-specific or numeric time-series compression architectures.

An additional primary-source check of [ZPAQ `libzpaq.cpp` component definitions](https://github.com/zpaq/zpaq/blob/master/libzpaq.cpp) shows distinct indirect context-map / indirect secondary symbol-estimation components (ICM/ISSE/MIX) rather than JLZ's simple two-source fixed-weight adaptive bit model. **Only SOURCE REVIEWED, NOT CODED or measured here**; the older JLZ adaptive context weight attempts and capped order-2 PPM tests are nearest known precedents. Any follow-up must quantify decoder serial-work impact and selected-domain conditional coding opportunities *before* building a complex model; generic fixed-weight tuning or another capped PPM model would be duplicates.
