## Structural hypothesis

Round 21/23 originally selected BWT followed by move-to-front, zero-run coding, and one native Huffman stream on original regions. A substantial part of approved Round 25's Silesia bytes is stored in these BWT regions. Test **new entropy arrangements on the already available MTF/zero-run stream**, without a new suffix-sort algorithm, extra compression backend, additional CLI settings, or changing rejected mathematical-match trials.

Two alternatives were screened:

1. **Native adaptive arithmetic** over the existing MTF/zero-run bytes, reusing JLZ's own bit-prefix adaptive arithmetic coder. Small sampled 256 KiB BWT blocks saved roughly 5–13% over the current single Huffman stream. A complete 12-file single-run archive candidate compressed to **60,672,443 B** (2,431,674 B smaller than Round 25), but took **10.718376 s encoding / 5.854392 s decoding in one run**. Its CPU burden relative to the accepted historical medians made it unsuitable for the more expensive ten-run stage. This is explicitly **screening only**, not a promoted result.
2. **Preceding-zero-context Huffman**, a cheaper alternative: classify each MTF/zero-run byte by whether the immediately preceding coded byte was zero. Encode the two subsequences separately using the *existing standalone native Huffman/raw/RLE packer*. Decode deterministically by choosing a subsequence based on the last reconstructed byte. Sampled blocks saved bytes at every tested location across nine representative Silesia files. The experimental `modeMixedCross` block type **14** carries the sentinel primary index, transformed symbol count and two independent packed streams; the decoder validates counts, context exhaustion and trailing bytes. Unchanged Round 25 decoder would reject this experimental type. The old three sample blocks were kept in their original Huffman representation to avoid needlessly recomputing already completed suffix sorts.

The second alternative justified one full **candidate-only** ten-run Silesia test. These are established Huffman/arithmetic/MTF/BWT concepts, not a new mathematical compression theorem.

## Verdict and next direction

**REJECT both BWT entropy coding variants.** A small low-overhead context split can save 1.59% of total Silesia bytes but appears to slow **both** encoding and decoding by ~3.7% compared with previously accepted performance, in addition to introducing a new incompatible internal block type. Adaptive arithmetic provides still greater size savings with disproportionate CPU penalties in a single screening run. The marginal economic return does not justify making either candidate the approved engine.

**Round 25 remains current: 63,104,117 B, 7.549920 s encode / 2.839905 s decode**, using the historical accepted methodology. Follow the user's Silesia-only/candidate-only benchmarking directives. Do not pursue more BWT entropy micro-partitions merely to gain another small percentage point. Next priority: inspect the **actual selected match literal/distance streams** and seek fundamentally larger reductions that do not add repeated costly coding passes. Review historic Round 18–20 selected-stream results first, and avoid theoretical estimates mistaken for archive wins.
