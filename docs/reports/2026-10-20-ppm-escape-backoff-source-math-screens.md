# Source-audited PPM escape/backoff architecture, native-Go screens

**Date:** 2026-10-20. **Status:** SCREENED and **REJECTED** the concrete bounded order-2 PPM prototype at both original-source/BWT and native mathematical-literal placements. **No integrated JLZ candidate, no ten-run benchmark, no production code, PGO or wire change.**

## Source-grounded architectural comparison and novelty

Inspected actual [7-Zip PPMd encoder `C/Ppmd7Enc.c`](https://github.com/ip7z/7zip/blob/main/C/Ppmd7Enc.c) Git blob `975157c9b33848506ab4c50fa4fb0875799bb8bd`, [ZPAQ `libzpaq.cpp`](https://github.com/zpaq/zpaq/blob/master/libzpaq.cpp) Git blob `523e363ecfd910d0a48789a136a898ca7b6654dc`, and [XZ/LZMA bitwise match-conditioned literal encoder](https://github.com/tukaani-project/xz/blob/master/src/liblzma/lzma/lzma_encoder.c), comparing to current JLZ `entropy/arithmetic.go`, `engine/match_tokens.go`, `engine/bwt.go` and the strategy ledger. No mature source code was copied/ported, no external compressor was executed as a backend.

**Novelty gate:** JLZ already encodes literal residuals predicted from the last reference, uses order-1 bitwise adaptive arithmetic and has tested static previous-byte rANS, online role tables, a bytewise Fenwick coder, a sparse LZP and PPM-like context splits. Do not relabel those as new discoveries. The specific previously *unscreened* architectural mechanism here is **variable-order byte-symbol escape/backoff from a high-order context to a lower-order context and ultimately an adaptive order-0 prior, with PPMd-inspired symbol exclusion**. This is not the full 7-Zip PPMd algorithm: the trial intentionally caps each order-1/2 context to 16 remembered distinct symbols, has a fixed one-count escape and no successor-context tree, SEE escape estimator, or PPMd run-length probability. ZPAQ's neural-like context mixers/MATCH/ICM/ISSE components were source-audited for their architectural difference, **not implemented**. In particular, observed failure of this bounded PPM must not be described as proof that PPMd or ZPAQ cannot improve JLZ.

## Executed reversible Go prototype

Disposable **original native-Go**, decoder-synchronous and independently bounded: three-level order-2→order-1→order-0 adaptive byte-symbol arithmetic representation with per-context 16-symbol bounded state, adaptive global 256-symbol model, count halving to prevent overflow, 32-bit E3 arithmetic interval and bit-level output, and matching inverse. The first variant used ordinary escapes; the second added actual **full exclusion** of symbols already seen in higher escaped contexts when coding all lower levels (including order-0). No model description or model tables transmitted; encoder and decoder train from reconstructed bytes. The separately counted output length allows one candidate subtype framing allowance of 8 bytes for original-source/BWT comparisons and 5 bytes for existing stream comparisons, **a favorable estimate, NOT a implemented JLZ framed subtype**. Actual integration would require additional archive tags, exact frame costs, corruption bounds and decode validation.

**Source identity:** all 12 complete *original* Silesia members were available unmodified, **211,938,580 bytes**, and all twelve SHA-256 identities matched committed `docs/reports/2026-10-18-round23-silesia-sha256.txt`. Selected **first/middle/last natural 256-KiB source blocks** from specified originals; every tested stream decoded back **byte for byte** and was verified by `bytes.Equal`. These are diagnostic source-block component tests, **not** full JLZ archive tests or actual automatic selection.

**Wins:** excluded source-original coding 0/36, excluded math literal 1/36, a **52-byte** favorable stream in a sampled Samba middle block; no-exclusion literal 1/36, also same small stream. The mathematical sample streams use the actual existing `tokenizeMatchV2` and `splitMatchTokens`, and are bytewise reversible with matching literal residual as well. Many of these sampled math tokens are *not* the currently selected output modes, so favorable per-stream wins are not end-to-end savings. Relative sizing is already very unfavorable even though proposed framing is underestimated.

PPMd-style exclusion reduced total math-literal output **3,919,962→3,772,886 B** over the same 36 streams, but still lost badly. Both source-symbol and mathematical-stream routes fail a large savings feasibility test without needing an expensive full integrated JLZ trial. The native mathematical matched-reference **residual** route was also reversibly screened in the no-exclusion trial, **4,701,433 B** total versus existing **2,453,528 B**, with **0/36 wins**; no reason to expand the losing variant to a full encoder mode. Observed native PPM source-block encode/decode cost was tens of milliseconds for a 256KiB block; those isolated timings are not a full-compressor speed claim.

## Disposition and follow-on architectural focus

**REJECT ONLY this bounded order-2 16-symbol/context fixed-escape coder at both tested surfaces.** The giant positive payload deltas prevent plausible integration without a fundamentally different probability/escape architecture. **Do not tune the 16-symbol cap, context hashing, escape constant or other adjacent parameters.** Full context-tree/SEE PPMd or a low-work sparse context mixer remain distinct theoretical architectures requiring compelling evidence, but are not automatically the next experiment; no ZPAQ mixer or full PPMd implementation was built. This study closes a concrete native coder, not the parent theory.

Do not mistake PPMd's favorable historical performance for an assurance that a naive PPM implementation will beat native BWT. Future investigation should return to the *remaining large competitor gap*: assess structural model and match-parse algorithms that demonstrably lower bytes **and** computational work on the actual dominant Mozilla/math, Webster/BWT and Sao/record-lane domains, with no blanket late entropy replacement. Favor algorithms that share the winning stream's existing parse work, not additional full encodings.
