# Round 20: Adaptive arithmetic mixtures and literal-run phase (not promoted)

**Date:** 2026-10-18. **Baseline:** approved Round 16, **66,519,205 B** Silesia archive total. **Decision:** REJECT model/format changes after low-cost selected-stream diagnostics. All permanent updates committed directly to `main`; the approved Go codec is unchanged.

## Research question

Can JLZ improve its selected match-block literal coding without re-running a matcher, adding a heavy grammar pass, or breaking the user-facing single automatic codec? Round 19 ruled out raw-source byte deltas and general byte-order-two contexts. Round 20 examines the bitwise **global/previous-byte** probability mixture that JLZ already computes, a grouped previous-byte intermediary, and the distinct statistics of literal bytes at different positions inside literal runs.

Experiments are **diagnostic only** against Round 16 **selected, finally emitted** `JLZ1` archive streams. Prequential code lengths are derived from probabilities via `-log2(p)` but are **not** actual arithmetic bitstream sizes. No candidate encoder or decoder was implemented, so there is no purported end-to-end win or promoted compression time. The existing standalone compressor was tested unchanged.

## A. Existing arithmetic context mixing weights

The approved `bitModel.probability` interpolates global and exact-previous-byte bit-prefix context probabilities with 1/8 local weight until that local context has 10 total counts, then 5/8. For every sampled bit, the same observed counters were used to evaluate alternative mixture weights. Sample: **9,617,227 decoded literal-stream bytes** from selected blocks, distributed across ten match-bearing Silesia files, bounded to roughly 1 MiB per file.

| Alternative local weight (early / mature) | Estimated coded-byte change from approved |
|---|---:|
| 1/8, 5/8 (approved) | 0 |
| 1/8, 6/8 | -44,866 |
| 1/8, 7/8 | -71,199 |
| 1/8, 8/8 | -72,285 |
| 2/8, 7/8 | **-75,030** |
| All-global context | +518,057 |
| All-local context | +10,592 |

Results vary materially by file. For example 1/8-to-7/8 mature weighting improved the sampled Dickens stream by 9,949 B and MR by 15,521 B, but worsened Mozilla by 5,801 B. No single fixed weight is universally optimal. Extrapolating to 39.56 MB total literal bytes *would not* establish a realized JLZ archive gain, and even proportional extrapolation suggests considerably less than 3% overall reduction. Changing decoding probabilities would require an explicitly tagged new arithmetic stream mode and backward-compatibility assessment. **Do not add a mode merely for this small diagnostic result.**

## B. Intermediate previous-byte group context

Evaluated a third binary prefix model that conditions on previous byte's high nibble (16 groups), low nibble, or broad ASCII character class. Mixtures combined global, exact previous byte, and group probabilities; observations update the same online counts on each bit.

Sample: **5,304,775 finally selected literal bytes** (about 0.5 MiB per grouped Silesia file).

| Mixing strategy versus approved | Estimated coded-byte difference |
|---|---:|
| High-nibble group; local 1/8 then 5/8; group 4/8 then 3/8 | -45,998 |
| High-nibble group; local 1/8 then 7/8; group 2/8 then 1/8 | **-55,120** |
| Low-nibble group, group 4/8 then 3/8 | -20,484 |
| Broad character class, group 4/8 then 2/8 | -35,421 |

Group contexts require a third adaptive probability estimate and more counter maintenance per coded bit; this is likely to increase CPU cost for an estimated gain of only tens of KB on the sample. Note sample size differs from A; **do not sum or directly rank absolute byte savings across A and B.** No candidate implemented.

## C. Literal-run position as a conditional context

Decoded **all 750 selected match blocks** from existing Round 16 Silesia archives (ten grouped files), walked packed opcodes and literal/copy lengths, and tagged every selected literal by position 0, 1, 2, or 3+ within its literal run. Compared static, idealized one-previous-literal-byte distributions, with and without this additional known phase context:

| Measurement | Value |
|---|---:|
| Selected literals examined | **39,562,459 B** |
| First literal in each run | 5,776,364 B |
| Second / third / subsequent | 3,941,860 / 2,937,694 / 26,906,541 B |
| One-previous-literal static idealized cost | 30,837,025 B |
| Previous-literal plus run-position static idealized cost | 29,893,039 B |
| Difference (idealized, no framing/model overhead) | **943,986 B** |

The phase signal is real, and may merit revisiting in a different architecture, but the apparent ~944 KB is an **in-sample static-model entropy estimate**, not a codec result, not a guaranteed upper bound on every possible adaptive implementation, and not necessarily incremental to JLZ's existing arithmetic prefix model. Using it requires supplying phase context to the entropy decoder during token replay instead of fully decoding the independent literal stream first, or sending separate entropy substreams with framing cost. Both increase CPU, complexity, and backward-decoder risk for a likely smaller **actual** gain. **Do not implement solely on this evidence.**

## Validation, comparator references, and limitations

- All three diagnostics completed successfully; scripts operated in disposable local source copies. `go test -count=1 ./...` and `go vet ./...` **passed against the unchanged approved Round 16 source**.
- No production format, decoder, source, or release changes. Therefore there are no new archival roundtrips to claim, and no ten-run encode/decode benchmark or CI Test release was run.
- Silesia: **12 files, 211,938,580 original bytes**. Approved Round 16 end-to-end archive: **66,519,205 B**; accepted ten-pair medians from its own benchmark environment: **13.290 s encode / 5.311 s decode**. These are *historical accepted* medians, not new measurements.
- Fixed historical comparator archives: **Zstd-3 66,216,569 B**, **XZ-6 49,233,340 B**. Their historical CLI timings: 1.256 s and 116.989 s, **not directly comparable** to in-memory JLZ timings.

## Decision and next target

**REJECT Round 20 as a source change. Keep approved Round 16 intact.** Adjusting mixing weights or adding intermediate byte-group context offers only modest estimated savings. Literal-run position exposes ~944 KB of idealized static conditional redundancy, but this alone does not justify rewiring arithmetic decode into token replay.

Prioritize a structural change whose *selected full-archive* savings can credibly exceed several megabytes, not repeated sub-1% parameter sweeps. Any future phase-aware joint model must demonstrate a compelling end-to-end cost and CPU model **before** implementing a new format. Avoid adding unused modes, DEFLATE/backends, or historical claims of “wins” based on entropy estimates.
