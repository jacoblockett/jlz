This report corrects the earlier `mozilla ELF` research labels: its dynamically linked `.so` members here are **DEC Alpha ECOFF**, specifically little-endian magic **0x0183**; verified using actual member bytes and external `file` identification. ## H1: sparse long-distance exact-copy overlay + established native JLZ regional coder (component screen)

Architectural reference: Zstd's rolling-gear long-distance matching, but no existing codec was run or used as a backend. An original sparse (one anchor every 32 source bytes) 8-byte fingerprint index finds **backward exact reference distances greater than 128 KiB** and replacement lengths **at least 128 bytes**, records exact `(position delta, source distance, length)` metadata, and replaces those source spans by zeros before feeding the entire transformed source to the **approved native JLZ encoder**. Decoder reverses JLZ then replays the exact backward copies in source order. All original-source bytes are restored with a real inverse; reference metadata is encoded as actual unsigned-varint records, not assumed free. This is a supplementary placement *before JLZ*, not a standalone external LZ encoder. Source matching/zeroing is experimental C++ and native JLZ encoding uses the current unmodified Go CLI; no experimental C++ is proposed for production.

- Full original Mozilla **51,220,480 B**: **1,523 long-range patches**, covering **800,149 raw source bytes**, metadata **11,684 B**; transformed input processed through native JLZ archived **18,371,759 B**, combined with metadata **18,383,443 B**, versus accepted original Mozilla **18,452,630 B**, saving **69,187 B**. Exact original restored after native JLZ decoding and back-reference replay. Experimental overlay finder measured **0.51 s** extra and ~**144 MB peak process memory** by `/usr/bin/time` before any JLZ encoding, making that gain uneconomic without significant additional changes.
- Original full Samba **21,606,400 B**: 663 long-distance patches, **379,344 B** raw span coverage, **4,983 B** metadata, transformed JLZ **5,116,078 B**, combined **5,121,061 B**, versus accepted **5,134,262 B**, saving **13,201 B**. Finder measured **0.20 s**, ~61 MB peak process memory. The source-level inverse was algorithmically identical; full independent replay was explicitly checked on Mozilla, but not separately rechecked after decoding Samba.

**REJECT this sparse overlay placement**: two complete original-file components combined yield only **82,388 B** archival savings before extra new-mode framing, and the extra scan alone costs ~0.71 s for the two files. Prior historical long-distance 512KiB history and sparse-anchor placement negatives remain, but this real reversible *global overlay* is a distinct diagnostic. Do not claim the broad LDM theory is disproven.

## H2: modular 32-bit additive invariance among Alpha words (coverage diagnostic only)

Independent original C++ diagnostic probes 4-byte-aligned 32-bit little-endian words at local 256KiB-block scope, hashes differences among the first four words, and verifies constant nonzero additive offset modulo 2^32 over later words. On full original Mozilla there were **287 occurrences** with >=64B translation-invariant runs covering a *maximum nonoverlapping* **35,828 B**, maximum run 2,996 B. Samba **50 occurrences / 5,520 B**, Sao **none**. This is a **verified exact source relation but NOT a complete reversible serialized codec**, and **35KB is an optimistic raw coverage upper bound before reference metadata**. Therefore do not integrate a new wordwise-additive match token or benchmark. Unlike JLZ's current constant byte XOR/ADD mask, the 32-bit group operation is distinct, but actual useful coverage is too small.

## H3: native source-aware tar/COFF partition and branch-relative transform (reversible experiments)

**H3a, class-separated native archives:** Original Mozilla USTAR members were moved into two reversible streams, all 118 Alpha COFF `.so` member spans grouped first, other 725 members second, with an exact self-delimiting original-order span map **1,898 B**. Both streams encoded by the accepted JLZ native engine: **14,382,671 B + 4,027,174 B + 1,898 B = 18,411,743 B**, only **40,887 B** smaller than selected incumbent Mozilla **18,452,630 B**. Exact source reassembly verified. Reordering entire binary members changes proximity of recurring code but is not a major gain. Further blind filename-category sweeps are not justified.

**H3b, four-way word-byte transpose after member grouping:** Reversible 4-byte lanes over the class-grouped COFF member stream were tested with the same approved JLZ native codec and exact transposed source lengths. Transposed COFF stream **16,435,338 B** (versus untransposed **14,382,671 B**), for a combined archive with other members + map **20,464,410 B**, **+2,011,780 B larger** than current Mozilla. A high-opcode-byte-first alternate gave **20,466,447 B (+2,013,817)**. This confirms existing cross-byte mathematical references matter more than simply grouping Alpha instruction bytes by position. These transposes are reversible by construction; this stage did not include a separate final inverse binary comparison.

**H3c, Alpha branch target normalization:** Parsed 118 real ECOFF `.text` section headers, recognized Alpha instruction opcodes **0x30..0x3F** (top six bits of each little-endian 32-bit word), and converted 21-bit word-relative displacements into section-position-relative target words modulo 2^21. Inverse subtracted the same section-position quantity. Changed **601,462 instruction operands**; **byte-for-byte inversion of the entire original 51,220,480 B Mozilla tar PASSED**. Feeding normalized bytes into approved native JLZ yielded **19,290,044 B**, **+837,414 B larger** than incumbent. **REJECT this Alpha branch normalization→existing full regional JLZ placement**. Distinct from earlier inappropriate x86 E8/E9 assumptions, but still an expansion.

## H4: source-aligned binary .text partition, integrated JLZ candidate (single full-corpus screen, REJECT)

This mechanism differs from whole member grouping. A genuine USTAR parser and 118 ECOFF section tables identify **23,975,888 B of `.text` code segments**; the other source bytes total **27,244,592 B**. Code and noncode streams preserve their own original source order; a sorted **118-span delta/length map costs 695 B** by actual uvarint serialization and restores the original exact tar bytes. Each independent stream uses the **existing JLZ automatic native encoder**. They code to **9,363,670 + 8,762,572 = 18,126,242 B** *before* the 695 B span map and any outer framing. The approximate standalone compressed size advantage is **~325KB** relative to incumbent 18,452,630 B Mozilla.

A **real original Go integrated temporary prototype**, in a disposable project tree, added `modeCoffTextPartition=20`, a bounded USTAR/COFF `.text` section discovery path, a new archive framing with exact metadata, two independently native JLZ-coded child streams and a fully checked inverse (including native archive SHA-256). The selector compares its complete serialized candidate to JLZ's existing regional archive. It only attempts the specialized candidate when the existing early regional pass is already successful; all other input modes and prior decoding paths remain intact. Both child native encoders were also tried concurrently, without meaningful elapsed-time improvement.

- **Original Mozilla entire-file candidate: 18,126,987 B**, saving **325,643 B**, with complete **byte-exact inverse PASS**. Single integrated full Mozilla encode took **3.9459 s** sequential-child version, **3.9039 s** concurrent-child version. This is *not* the accepted Mozilla timing.
- **Complete original 12-file Silesia one-pass integrated candidate: 58,442,096 B**, **72.4249846%** original reduction, versus accepted **58,767,739 B /72.2713349%**. All **12/12 complete input files restored byte-exactly**. One complete original-corpus candidate encode timing **6.825599 seconds** versus historical accepted ten-run median **4.787371 seconds**, nominal **+42.58% encoder time (worse)**; no timed complete-corpus candidate decoder median, no ten-run series, no new Windows/race/full tests. This one-run timing comparison is diagnostic and cannot constitute a qualified regression median, but the massive redundant coding work makes this candidate economically unpromising even with unpaired session noise. All metadata and both child archive envelopes are charged in the 58,442,096 B value. No new source mode 20 was committed.

**REJECT H4 implementation**, despite real 325KB space improvement. The format, tar/COFF parser, new decoder, two full native child encodings and extra buffers are a substantial complexity burden for 0.554% whole-corpus archive savings and an enormous apparent encoding penalty. Distinguish *evidence that structure helps* from approval to integrate this specific expensive placement. Do not tune span thresholds, parallelism or Alpha opcode ranges as the next research family.

## H5: remove transformed XOR/ADD match searching, exact-only math parser (one complete original-corpus screen, REJECT)

Audited actual **selected** match-mode opcode columns in the previously approved complete Mozilla archive (196 original 256KiB blocks; 192 selected mathematical, 4 previously accepted lane modes). The final math streams had **2,047,244 literal commands**, **1,462,373 direct exact-copy commands**, **1,145,396 repeat-distance exact-copy commands**, but only **1,297 XOR/ADD transformed references** (214 + 1,011 direct and 8 + 64 repeat). Actual `match.LikelyTransformedMatches` gate was positive for **21 of 192** selected math blocks; its total sampled gate time on original Mozilla was **0.102 seconds**. The gate efficiently excludes transformed-index work on most blocks already; selected token streams with cross-block histories can differ from independent block gate tests. This explains why a wholesale replacement of transformed matching looked promising from global opcode frequency but was not.

A genuine experimental Go source changed the existing tokenizer to use exact-only reference indexing everywhere, reusing the *entire* native math entropy/region pipeline without changing the decoder. Single complete original twelve-file Silesia candidate pass: **58,789,865 B**, **+22,126 B** archive regression against accepted **58,767,739 B**, encode-time **5.211775 s** (single candidate-only run), full original byte roundtrip **12/12 PASS**. Not a ten-run qualified candidate; rejected after losing bytes and showing no convincing overall speed gain. File changes included Mozilla **18,452,630→18,472,075 B (+19,445)**, ooffice **2,692,252→2,699,583 B (+7,331)**, Samba **5,134,262→5,129,612 B (-4,650)**; other files unchanged. This is **a direct integration screen**, not a theoretical argument against more efficient reference search.

## Decision and actionable next experiment

**REJECT H1, H3 specific placements, H4, H5. H2 is a diagnostic noncandidate.** Positive insight: COFF `.text` separation beats same-group mathematical encoding when candidate source bytes are sorted by true native binary sections, but the naive solution duplicates heavy regional compression. A future meaningful native approach would have to **reuse incumbent match work and exploit the code/noncode distinction within currently emitted streams without independently re-encoding two complete archives**. Investigate cheap contextual partitioning of already selected literal/sequence models, using CODEC-independent stream coordinates or low-work statistics, before implementing another full tar parser. Full accepted JLZ with confirmed source baseline remains **58,767,739 B / 4.7873709325 s / 1.8721679705 s** (historical ten runs).
