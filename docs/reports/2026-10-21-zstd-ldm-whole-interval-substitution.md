# Zstd LDM group source intervals and shared discovery: source-verified integrated screens

**Date:** 2026-10-21. **Disposition:** REJECT literal-gap interval substitution and this repeated source-producer placement as an accepted production improvement; standalone source and full-codec implementations were actually run, verified and preserved only in disposable local experiments. **Zstd LDM family remains OPEN for genuinely different high-value placements.**

## Architectural origin, novelty and expected limits

Meta Zstd source [`zstd_ldm.c`](https://github.com/facebook/zstd/blob/dev/lib/compress/zstd_ldm.c) precomputes long match sequences; [`zstdmt_compress.c`](https://github.com/facebook/zstd/blob/dev/lib/compress/zstdmt_compress.c) delivers source-side sequences to parallel jobs. Earlier JLZ **G1/S2** group-local sparse anchors were implemented and screened, and four follow-on FORCE / FORCE+INSERT-SKIP / DIRECT-INDEX / MAXIMAL probes were **already rejected** in [2026-10-21-zstd-ldm-sequence-injection.md](2026-10-21-zstd-ldm-sequence-injection.md). In particular, do not repeat sparse match insertion as a supposedly new idea. The genuinely distinct question here was whether a **source-verified list of adjacent long-copy commands plus literal-only short intervening gaps** could be scheduled **as a whole parse interval**, entirely avoiding matcher and lazy-search work on those gaps. A second modification reused the same producer's existence evidence as a substitute for an independent cross-region preflight, not simply another bucket/stride tuning.

The independent original-Go source diagnostic scanned all twelve complete original files in four-region 1MiB independently reconstructible groups, using an 8B exact key, 16B source sampling, long match eligibility distance >128KiB, length >=64B, maximum 32KiB. Skipped newly covered source positions to count **nonoverlapping** long source matches. This screen found **12,143** sparse source matches covering **1,673,230 B source**, segmented into **9,858 clusters using 256B gap criterion**, with only **2,285 candidate pair bridges** totaling **212,098 gap bytes**; the actual source scan took **1.406 s** in that standalone run. Coverage is **not incremental archive savings** and includes files whose preferred encoding is BWT. No old report had measured *bridgeable sequence intervals*, unlike broader historical sparse far-match byte totals.

## Actual native JLZ implementation and verified variants

On a source snapshot with all original production Go blobs (`engine/match.go`, `engine/regions.go`, `engine/region_fast.go`, `engine/cross.go`) and committed root `default.pgo` **Git-object identical to current live main**, a research-only Go file `engine/zstd_ldm_interval.go` builds a group-local, once-per-group immutable array of source-verified far commands for at most four existing 256KiB region jobs. Two previous 8B candidate positions are retained by key, verified against original bytes and capped at 32KiB per reference. For qualifying candidate blocks the existing `tokenizeMatchV2Range` engine continues exact, XOR, ADD, lazy selection and original entropy/coding of ordinary positions, while an external far hint replaces matching at a verified position. **Explicitly bound the ordinary matcher index to the existing last 128KiB** to avoid the already documented accidental historical R63 wide-index collision. Decoder now supplies reconstructed earlier same-group bytes to native match expansion; the four-block independence boundary is unchanged.

- **CLUSTERED-BRIDGES**: after each emitted far reference, if the next precomputed far command begins within 256 source bytes, emit the gap as an ordinary literal without running regular match/lazy search in that gap. Entire command/gap interval is substituted.
- **NO-BRIDGES**: identical precomputed verified far commands but retain native matching on every interstitial byte. This isolates the clustered literal-interval substitution benefit, rather than disguising it as far-hint benefit.
- **SHARED-GATE**: NO-BRIDGES plus evidence short-circuit of redundant `crossPotential` preflights where >=2 producer hints already suffice to consider group-history mathematical encoding. Tries to reuse producer findings before recomputing another map. Same source/grammar, not a new corpus data dependency.

All three variants were **actually integrated into the full native JLZ compressor and candidate decoder** and ran independently on all twelve complete original Silesia archives, with full per-file JLZ framing/metadata and exact `bytes.Equal` source restoration. All 12 SHA-256-identified corpus originals (211,938,580 B) matched the repository manifest. Only mozilla, samba and ooffice sizes changed. The other **nine** file lengths matched accepted JLZ; every compressed file, including ooffice, roundtripped exactly.

**Actual incremental interval result:** forcing short gaps to literals made the archive **10,115 B larger than NO-BRIDGES (worse)** while avoiding searches in only limited bridgeable intervals. The producer-backed shared preflight retained exactly the NO-BRIDGES **per-file lengths** but showed no repeatable speed benefit. The NO-BRIDGES size improvement is also less than prior S2's improvement, and one complete file regressed by **6 B**:
- Mozilla: accepted **18,452,630 B** to NO-BRIDGES **18,375,611 B** (**77,019 B smaller, better**).
- Samba: accepted **5,134,262 B** to NO-BRIDGES **5,130,383 B** (**3,879 B smaller, better**).
- Ooffice: accepted **2,692,252 B** to NO-BRIDGES **2,692,258 B** (**6 B larger, worse**).
- Nine remaining files: same compressed sizes as accepted JLZ.

A separate direct actual-producer study ran `groupFarIntervals` across the 12 complete original source files, not merely artificial slices: it generated **46,412 raw verified candidate hints**, **384 blocks with >=2 hints**, **4,614 close pair opportunities** before actual command selection, requiring **1.619763 seconds total** of standalone wall-clock producer work. That is diagnostic source discovery cost, **not measured integrated incremental CPU**, because not all candidates or modes execute it. A bounded 4-region producer is cheaper than full-file discovery but still cannot justify itself purely by 0.038pp compression gain and does not prove a CPU reduction.

## Correctness, compatibility, performance and stop decision

The NO-BRIDGES candidate **PASS**: `go test -count=1 ./...`; `go vet ./...`; `CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build` (cross-build, no Windows runtime); and bounded `go test -race -count=1 ./engine -run '^TestMatchV2OverlappingRepeatAndTransforms$'`. A broader four-pattern targeted race command **timed out after 180 seconds**, with no completion record: **NOT PASS, not claimed**. Existing archive compatibility, corruption and truncation tests were included in the passing uncached Go suite, but a separate new-archive-to-old-decoder interoperability test was not performed. Existing old archive decode should remain supported by new decoder. **New archives with >128KiB references may not decode under the existing production decoder**, so a new properly versioned format would be required before acceptance. The experimental code never entered main.

**REJECT the literal-only interval bridging architecture at this placement**: it loses 10,115 B relative to keeping current near parsing, and the source-producer overhead plus decoder compatibility cost do not purchase a demonstrated throughput improvement. **DEFER the group-hint-only NO-BRIDGES variant** as no better than already-tested G1/S2; do not repeat it as a different new name. Shared-gate query routing is another real source placement but retains archive sizes and has not established CPU gain. This **does not exhaust** all of Zstd's source sequence and dictionary design. Genuinely open alternatives require a different high-impact source feature: e.g. a shared native match-state rolling window with proven end-to-end work elimination, costed command-boundary superblocks, or a source-domain transform that improves regions not already covered by G1/S2. Do not sweep 32/64/128/256 literal-gap thresholds or shallow hash parameter values as novelty.

Retained references: accepted JLZ **58,767,739 B / 4.7873709325 s encode / 1.8721679705 s decode**; Zstd-3 **66,216,569 B /1.2561/0.8551 s**; XZ-6 **49,233,340 B /116.9892/2.3079 s**, historical and **not rerun**. No candidate selected for 10-run qualification, no production Go change or PGO change.
