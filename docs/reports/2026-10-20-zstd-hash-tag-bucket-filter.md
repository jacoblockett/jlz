# Zstd row/tag matchfinder inspiration: native packed fingerprint tag with exact same match candidates

**Date:** 2026-10-20. **Status:** original Go prototype, complete original-Silesia corpus byte-exact and 2× same-session paired full-corpus timing screens. **Concrete packed two-position tag variant REJECTED as a demonstrated improvement**; general Zstd row-hash/SIMD search not exhausted. No production code or archive change.

## Novelty and source basis

Examined actual Meta Zstd [`zstd_lazy.c`](https://github.com/facebook/zstd/blob/dev/lib/compress/zstd_lazy.c), [`zstd_compress.c`](https://github.com/facebook/zstd/blob/dev/lib/compress/zstd_compress.c), and [`zstd_double_fast.c`](https://github.com/facebook/zstd/blob/dev/lib/compress/zstd_double_fast.c), with its row/tag-bucket matchfinder, multiple candidate probes, and cache-aware matching. The existing JLZ match index is already compact: **two recent 32-bit source offsets per 64-bit hash bucket**, separate exact/XOR/ADD candidate tables. It was accepted over the older 12-byte variant; naive larger hash rows and deeper buckets were historically unattractive. This trial does **not** increase candidate depth, change hash width, skip any source position, or replace JLZ's mathematical parser. Rather, it preserves the same bucket size by using **24 bits for a bounded input-relative 1-based position plus eight low bits of its 32-bit fingerprint as a rejection tag**. The existing hash bucket index uses different/high bits of a hash, so the extra stored tag can reject many independent hash collisions before dereferencing the source. If entire input length is at least 2^24, the experimental index uses unchanged full32-bit positions to preserve arbitrary-input correctness.

**Exact candidate preservation argument:** any real five-byte exact/XOR/ADD match verified by JLZ's 4/5-byte anchor necessarily produces the same normalized `match.Fingerprint(data, pos, typ)` at source and target. Therefore its stored low-eight-bit fingerprint tag matches. Any omitted tagged-out candidate would have failed the original anchor comparison anyway. Every actual bitstream should be identical; a false positive tag merely continues to the original anchor check. This is a different Zstd-inspired **constant-size rejection cache** idea from earlier failed fast exact-only dualhash parser replacement and earlier new row-depth experiments.

## Tested complete original corpus and paired controls

Used user-supplied original complete twelve Silesia files, 211,938,580 original B, canonical SHA-256 manifest already checked 12/12, accepted JLZ Go source `engine/match.go` Git SHA `6c9714114a056bf49f8124f81826f0eded68a5d8`, committed root `default.pgo` unchanged. Only a disposable copy of `engine/match.go` and diagnostic `engine/zz_zstd_tag*_test.go` changed; no production or mode change. Every measured test encoded/decoded **all 12 originals** and asserted exact source bytes. Single tagged pass **58,767,739 B**, exactly identical complete accepted archive bytes in size on each original. Single-pass encoder 5.378704819s/decode1.96178694s, **NOT new ten-run baseline**.

For controlled comparison, within one Go test process and compiled using explicit `-pgo=./default.pgo`, alternated enabled packed tags vs disabled legacy exact source-index storage by source file while encoding and decoding every original in both cases. ## Scoped decision and Zstd continuation

**REJECT/DEFER only the current 8-bit fingerprint tag packed in a two-entry 64-bit bucket**: it preserves archive size exactly but cannot demonstrate consistent full-JLZ encoding speed wins even in two paired tests, and adds an offset-width compatibility branch to an already well optimized hotloop. **Do not generalize to all Zstd row- or chain-based tag matchers**, which can batch multiple hash comparisons and prefetch cache lines. To justify a bigger-row alternative, first quantify current collision/anchor rejection cost and evaluate preserved exact+XOR+ADD candidates without paid extra search or mode regressions; do not confuse it with the previously rejected **different-parser** dualhash exact-only replacement.

Current JLZ remains **58,767,739 B / 4.7873709325s encode / 1.8721679705s decode**, historical ten-run reference; Zstd-3 **66,216,569 B / 1.2561 / 0.8551s**, XZ-6 **49,233,340 B / 116.9892 / 2.3079s** historical externals unretested.
