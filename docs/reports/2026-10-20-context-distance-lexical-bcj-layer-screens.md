## H1: contextual four-entry distance cache layered on current math tokens

**Closest earlier work:** opcode-conditioned native distance splitting and length-conditioned distance models were previously screened as low-value; native three-entry global repeat-distance cache already exists. This experiment does **not** replace match discovery or that repeat cache. It substitutes an additional **last-decoded-byte keyed, four-entry move-to-front distance cache** for explicit distance *metadata only*. Context cache entries are updated for **all** references, including implicit recent-offset references, so encoder and decoder reconstruct identical cache state. When the explicit distance is in the keyed cache, a tag 1..4 substitutes for it; otherwise tag 0 and the ordinary exact varint are emitted. Previously existing transformed-repeat-index bytes remain in the escape stream.

**Reversible native Go proof of concept:** parse already emitted current V2 tokens; form context-index and escaped-varint streams; charge **actual `packFiniteState(tags)` + `packVarintStream(escapeBytes)` + one mode-selector byte**, compared with current **`packVarintStream(st.distances)`**. Independently replay the opcodes, lengths, masks, and literal bytes, expand each reference from the reconstructed *decoded prefix*, reconstruct original distance bytes, and validate both distance-column identity and exact source reconstruction. This is **a real synchronized inverse**, not an original-data-based decoder assumption.

**Original Silesia first/middle/last 256 KiB math-block diagnostics** for complete files mozilla, samba and ooffice: **9/9 inverse PASS**, **47,401 explicit distances**, **1,068 contextual cache hits (2.25%)**. Current packed distance components **80,267 B**; candidate components including all new stream frames and selector **80,256 B**, only **11 B saved** across nine blocks. Individual file totals: mozilla **20,418→20,425 B (+7)**; samba **24,166→24,027 B (-139)**; ooffice **35,683→35,804 B (+121)**. Four block wins could at most save **154 B** under a favorable per-block selection before further decoder-format complexity. Candidate context table is 256×4 distances = 4 KiB of decoder state and adds lookups and a second entropy stream. **REJECT placement**; avoid cache-capacity/context-width tuning.

## H2: adaptive source-word dictionary layered before existing BWT

**External architectural inspiration:** Kanzi `TextCodec` pretransforms repeated words, which JLZ does not currently place before its original-byte BWT path. Different from historical grammar on match lengths, selected literal residuals and LZP-before-BWT. This is source-byte lexical preprocessing, not another standalone compressor.

**Reversible native prototype:** per 256 KiB original block count exact ASCII alphabetic tokens (4..24 bytes), choose up to 64 with frequency >=8 and positive gross byte savings; stable sort by projected savings then lexical tie-break; emit dictionary (count and exact word lengths/bytes), plus original transformed size; substitute selected words by **0xFF,index**, escaping literal 0xFF as **0xFF,0xFF**. Encode transformed bytes with JLZ's **existing `encodeBWTSubregions`**, charge BWT mode, additional outer mode and dictionary metadata. Inverse existing BWT mode and dictionary transformation, compare whole restored original bytes.

**Original Silesia distributed first/middle/last samples** of full dickens, webster, reymont, xml and nci: **15/15 exact inverse PASS**, current same-stage BWT **598,751 B**, lexical-transform+BWT **601,793 B**, **+3,042 B**. File component deltas: dickens **+1,987**, webster **+937**, reymont **+430**, xml **-191**, nci **-121**. Only 6/15 individual blocks won, with a favorable per-block oracle saving at most **459 B** before decoder/selection overhead. Crucially, raw text shortening does **not** imply smaller BWT/MTF/entropy bytes, and the dictionary preparation is additional encoder work. **REJECT concrete dictionary layer**; no size/speed justification for format integration.

## H3: add 0F 80..8F near-conditional-branch normalization AFTER accepted E8/E9 BCJ

**Closest accepted feature:** the already accepted E8/E9, four-byte relative-address normalization before BWT. This tests an actual different near-conditional branch marker family, **not** tweaks to the old opcode-density threshold. Original full ooffice has approximately 24,445 occurrences of 0x0F followed by a byte 0x80..0x8F before skip-overlap filtering. A new second reversible pass converts its following 32-bit displacement to the position-relative absolute target modulo 2^32 and skips that operand. Inverse **reverses the Jcc pass first, then reverses the accepted E8/E9 pass**, preserving byte-exact input even for arbitrary non-executable byte sequences.

**24/24 entire original ooffice 256 KiB blocks PASS** the two-pass inverse and **24/24 transformed BWT outputs PASS** existing full inverse. Existing `BCJ→BWT` component baseline **2,701,751 B**; candidate `BCJ→Jcc→BWT` **2,721,284 B**, **+19,533 B**. Only 1/24 block improved (38 bytes); one tied. This is **not** the final ooffice JLZ archive size: other selected current modes and global framing matter. **REJECT placement**, no additional mode or codec code on main.

## Decision

**REJECT H1, H2 and H3 as production changes.** All reversible components were genuinely executed with existing native encoders and charged metadata; their sizes do not plausibly fund additional encoder/decoder work or format complexity. No complete candidate-only ten-run benchmark was warranted. The underlying general contextual references, lexical transforms and executable prefilters are not universally disproven; only these concrete placements are closed. Pursue a structurally different high-impact mechanism rather than adjacent cache capacities, dictionary sizes or conditional-jump threshold sweeps.
